# Operational gate #42 — 100-package corpus load test

This is the first recorded run for the gate “Real load testing with 100+ package
corpora.” The run completed on 2026-08-15. Its canonical, timestamp-free machine
record is [`loadtest-100-2026-08.json`](loadtest-100-2026-08.json).

**Gate verdict: PASS.** Leitir materialized, load-time validated, searched, and
integrity-rechecked 116 distinct pinned package/source corpora. This exceeds the
100-package threshold.

`github:owner/repo@40-hex-SHA` pins. Release tags were resolved to the listed
commit SHA through authenticated GitHub API requests before the run; the run then
used only those exact SHAs. All sources are GitHub repository source types, with

The release-pinned corpus contains small and medium libraries, frameworks, CLI
tools, and database projects. 116 pins resolved and materialized; 87 resulting
shelves were fully `verified` and 29 were `sampled`, as recorded by Leitir’s
manifest verifier. The two unsuccessful pins were `scikit-learn` and `scipy`;
each exhausted the harness’s five-minute `get` subprocess limit on the final
warm-cache evidence pass. They remain failures rather than being counted or
silently retried as successes.

## Method

The stdlib-only `tools/loadtest_corpus.py` processes sources serially in sorted
source order. For each pin it:

1. invokes `python -m leitir.cli get --json --root …` and requires one exact
   result at its canonical shelf location;
2. records shelf file count, byte count, manifest SHA-256, and verification
   state after `read_valid_manifest` accepts the shelf;
3. runs three absent, fixed literal needles through `ScopedSearcher` using an
   offline local shelf tree. Every supported source file is therefore scanned,
   while absent needles avoid a misleadingly large result-list allocation;
4. attempts a trigram index only after `require_eligible`; and
5. performs a separate timed `read_valid_manifest` integrity re-check.

The fixed needles were
`__leitir_loadtest_needle_a4f8__`,
`__leitir_loadtest_needle_b7c2__`, and
`__leitir_loadtest_needle_d9e6__`. Each produced zero hits across the 116
successful shelves, as intended. All 116 index attempts were correctly marked
`skipped_ineligible`: direct GitHub shelves have `parity: unknown` rather than
the `parity: exact` index-eligibility requirement. This is a policy result, not
an index-build success claim.

The final evidence command was:

```console
PYTHONPATH=src uv run --no-project --with-requirements requirements.txt \
  python tools/loadtest_corpus.py --allow-existing \
  --root /tmp/opencode/loadtest-root \
  --output docs/evidence/loadtest-100-2026-08.json
```

Environment: CPython 3.14.6; Linux 7.0.0-28-generic x86_64 with glibc 2.39;
16 logical CPUs; worktree base `e740308b2d00e5682f75cb2135c46a12368f41a2`.

## Failure analysis and limitations

- **Failures (2):** `github:scikit-learn/scikit-learn@1fecc100…` and
  `github:scipy/scipy@92d2a859…` timed out during materialization. The aggregate
  records them under `timeout`; neither supplies shelf, search, index, nor
  integrity metrics.
- **Warm-cache materialization:** an initial clean-root attempt established much
  of the shelf corpus but exceeded the outer evidence-command time budget before
  publishing a complete report. The published pass deliberately uses `--allow-existing`
  (recorded as `root_mode: "allow_existing"` in JSON). Its `get` timings thus
  include cache hits and must not be interpreted as cold-network download
  performance. Search and integrity phases still execute against every local
  shelf in this recorded pass.
- **Single machine/network path:** wall times include this host’s filesystem,
  GitHub availability, network cache, scheduler, and Python version; they are
  not a throughput SLA or a cross-platform benchmark.
- **Index coverage:** zero shelves satisfied the existing exact-parity index
  policy, so this run exercises the required ineligible branch but does not
  benchmark a successful index build.
- **Query workload:** absent literals measure exhaustive local enumeration and
  byte scanning with bounded result fan-out; they do not represent a typical
  high-hit user query.

Despite those limits, the gate criterion is about real corpus load scale, and
116 real pinned corpora completed all required load, local search, and manifest
validation phases. The gate therefore passes.
